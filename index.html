Abblo API & Activities Reference

Cómo el frontend web de Abblo habla con el backend — cada endpoint que llama, la forma exacta de cada petición y respuesta, y en particular cómo funciona el motor de Actividades: el esquema de contenido, el flujo de envío de respuestas, y cómo se registran los intentos. Escrito para el equipo que está construyendo Abblo Mobile.

Hecho leyendo el código fuente del frontend en producción (abblo-frontend-jesus-trocha) y capturando en vivo una petición/respuesta real de una lección real. Donde el código del frontend no revela algo, se aclara explícitamente en vez de adivinar.

Convenciones de las peticiones

Toda petición pasa por un único wrapper, customFetch (src/services/fetch.ts). Algunas reglas aplican a todos los endpoints de abajo salvo que se indique lo contrario:

Base URL

Se elige con una bandera definida en tiempo de compilación: VITE_DEV === "on" → API de dev (pabbloapi.americana.edu.co/api/), si no, producción (sauco.abblo.com.co/api/). Cada ruta de abajo es relativa a esa base — ej. user/me en realidad significa https://sauco.abblo.com.co/api/user/me.

Header de auth

Casi todas las llamadas envían Authorization: Bearer <access_token> más Content-Type: application/json. Las pocas que suben un archivo (login, subida de foto) envían multipart/form-data en su lugar, sin header de Content-Type explícito.

Comportamiento en 401

Un 401 en cualquier petición borra inmediatamente toda la sesión y fuerza un nuevo login. No hay ningún flujo de refresh-token en este frontend — si la app móvil quiere re-autenticación silenciosa, eso necesitaría soporte del backend que no parece usarse aquí.

Paginación

No hay un constructor de queries consistente — la mayoría de los endpoints de listado se llaman con strings armados a mano como ?page=1&per_page=100&order_by=name-asc. Trata page, per_page, order_by=field-asc|desc y varias claves filter_by_* como la convención de facto.

Descarga de archivos. Solo un endpoint devuelve un archivo binario (el reporte Excel grupal del docente) — usa una ruta aparte, customFetchFile, que lee un Blob en vez de JSON. Todo lo demás en este documento es JSON.

Modelo de datos central: Course, Level, Group, Enrolment

Estos cuatro conceptos aparecen en casi todos los endpoints, y el equipo móvil necesita tener clara la diferencia antes de que cualquier otra cosa tenga sentido.

Nivel (level_course)

Un sub-nivel del currículo CEFR — el contenido en sí. Compartido por todos los estudiantes que lo cursan. Los nombres reales se ven así: "Elementary A1.1" o "Intermediate B1.1". Tiene id, name, ordering (su posición, base 1, en todo el currículo).

Grupo (group)

Una clase/cohorte específica cursando ese nivel: un docente, un code, un period (periodo académico), fechas de inicio/fin, y una group_password para auto-matricularse. Lleva crucialmente is_active — si este es el grupo que el estudiante debería estar usando ahora mismo.

Matrícula (Enrolment) = un emparejamiento (Nivel, Grupo) para un estudiante. Un estudiante puede tener varias filas de matrícula para el mismo nivel a lo largo del tiempo (repitiéndolo, cambiando de cohorte) — solo una debería tener group.is_active: true por nivel a la vez.

Por qué importa: casi todos los endpoints de contenido están indexados por id de grupo, no de nivel — group/{idGroup}/units/activities, group/{idGroup}/user/{idUser}/grades, activity/{id}/group/{idGroup}/attempt. El móvil siempre debe resolver "mi grupo activo para este nivel" a partir de enrolments antes de poder pedir cualquier contenido — el id de nivel solo no alcanza.

Flujo antes del Home

Qué pasa desde que se abre la app hasta que se llega a /home. Es el flujo que hace la web hoy, leído del código; no incluye lo que haga la app móvil por su cuenta.

1

Login

POST auth (identification_number + password) y, con el access_token recién recibido, GET user/enrolments. Se guardan token, datos del usuario y matrículas. Al entrar a la pantalla de login la web limpia cualquier sesión anterior. Si la petición de matrículas falla, quedan [] y no se muestra nada.

2

Siempre se pasa por /welcome

Estudiantes y docentes por igual. No existe la regla "si no tiene matrículas, ir a welcome": todo el que inicia sesión llega ahí. La regla antigua que saltaba directo a /home si ya había grupo activo está comentada.

3

Elegir curso

GET course/all. Al tocar un curso se guarda idCourse y un idLevel provisional: el nivel de la matrícula activa de ese curso (o undefined si no hay). No hay petición ni navegación; solo cambia la pantalla.

4

Elegir nivel

GET course/{idCourse}/levels, ordenado por ordering. Al tocar una card: si en enrolments hay una matrícula activa (group.is_active) de ese nivel, se guarda idLevel y se navega a /home. Si no la hay, no pasa nada (clic muerto en el código actual).

5

Unirse a una clase (/welcome/classes)

Solo se llega por URL; ninguna pantalla enlaza hoy a ella. Pide GET levelcourse/{idLevel}/groups?page=1&per_page=6&order_by=group.name-asc (se muestran los que tienen offered e is_active) y GET user/enrolments para marcar en cuáles ya está matriculado. La persona escribe la clave de la clase y se envía POST coursetoken/enroll con { id_group, token, group_password }. Si sale bien: se vuelve a pedir user/enrolments y se navega a /home.

6

Home

Con idLevel definido, busca la matrícula activa de ese nivel (ver Cómo resolver el idGroup) y pide me/position, units/activities y progress/me. Si no encuentra matrícula activa no redirige a welcome: muestra un dashboard vacío o parcial.

El flujo del token está desactivado en la web. Canjear el token enviado por correo (GET coursetoken/info/{token}, modal de token, unir lo recibido a enrolments y navegar a clases) está comentado en LevelsWelcome.tsx. Por eso dataCourse.tokenLevel nunca se llena y el campo token de coursetoken/enroll viaja como "". La pantalla móvil "selecciona tu nivel y escribe el token" no tiene un equivalente activo en el código web: su contrato (qué devuelve la validación del token y cómo se relaciona con id_group) hay que confirmarlo con backend, no deducirlo de este documento.

Otros detalles del flujo

  • Registro: POST user y luego se manda al login; la persona no queda con sesión iniciada y debe hacer los pasos 1 a 6.
  • Estado persistido: el estado de Redux se guarda en localStorage, así que idCourse e idLevel sobreviven a una recarga. /welcome/classes depende de eso.
  • Sesión vencida: un 401 en cualquier petición limpia la sesión y regresa a la pantalla inicial.
  • Docente: usa las mismas pantallas welcome (curso → nivel). Un docente sin matrículas queda atascado en el clic muerto del paso 4; no hay un atajo específico para docentes.

Cómo resolver el idGroup

Casi todos los endpoints de contenido llevan el id de grupo en la URL. El frontend web nunca usa enrolments[0]: el grupo se deriva siempre del nivel que la persona seleccionó, buscando en enrolments la matrícula de ese nivel que esté activa.

const idGroup = enrolments.find(
  (e) => e.level_course.id === selectedLevelId && e.group.is_active === true
)?.group?.id;

// luego, por ejemplo:
GET group/${idGroup}/units/activities
GET group/${idGroup}/user/${idUser}/grades
GET activity/${idActivity}/group/${idGroup}/attempt
Error común: enviar siempre enrolments[0].group.id. Eso hace que, sin importar la card/nivel que la persona elija, todas las peticiones lleven el mismo grupo (el del primer enrolment del arreglo) y el backend responda con el contenido de ese grupo en vez del nivel seleccionado. El orden de user/enrolments no tiene ningún significado funcional.

Reglas que sigue la web

  1. Cambia el nivel → se recalcula el grupo. Al hacer clic en una card de nivel (Levels.tsx), al cambiar de nivel en el selector del header (NavLevels.tsx) y en el Home según el idLevel actual, se vuelve a buscar el idGroup y se vuelven a pedir units/activities y grades.
  2. Sin matrícula activa para ese nivel → el nivel está bloqueado. Si el find devuelve undefined, la web no navega y muestra "This level is not active". No hace fallback a enrolments[0].
  3. Varias matrículas del mismo nivel: solo cuenta la que tiene group.is_active === true. Las anteriores (otros periodos) son historial. Si hubiera más de una activa para el mismo nivel, la web toma la primera que devuelve find.
  4. Pantalla "selecciona tu nivel y escribe el token": es el flujo de matrícula. La persona elige nivel → grupo/clase y escribe la clave; se envía POST coursetoken/enroll con id_group y group_password, se vuelve a pedir user/enrolments y a partir de ahí el grupo se resuelve por nivel como arriba.
  5. Único fallback (último recurso): si no hay idGroup en el estado, el servicio de actividades busca la matrícula del nivel actual y, si tampoco, la primera con group.is_active. Es una red de seguridad, no el camino normal.

Se pide justo después del login (y de nuevo al unirse a una clase nueva). Devuelve el arreglo de matrículas mostrado arriba.

Perfil del usuario actual — anidado bajo profile, a diferencia de la respuesta del login:

POSTuser

Registro. Cuerpo: { first_name, last_name, email, password, id_rol, user_terms, promotions, id_identification_type, identification_number, cellphone, birth_date, id_country, is_active }.

Perfil y foto

PUTuser

Actualizar el propio perfil. Cuerpo: { id_user, first_name, last_name, email, cellphone, id_identification_type, identification_number, id_country, birth_date, username, id_rol, is_active, about_me }. Sin id en la URL — el backend infiere el usuario a partir del token.

POSTuser/image

multipart/form-data, campo image_file. Validación del lado del cliente antes de subir: solo png/jpg/jpeg, máximo 2 MB. La respuesta no trae la URL firmada nueva — siempre hay que seguirla con GET user/me.

DELETEuser/image

Sin cuerpo. Limpia img_big/img_small del lado del cliente si tiene éxito.

Nota de CORS sobre el bucket de DigitalOcean Spaces: las fotos de perfil se sirven desde resources-abblo.nyc3.digitaloceanspaces.com como URLs pre-firmadas. Cargan bien como <img>/en cualquier navegador, pero leer sus bytes desde JavaScript (canvas, fetch, cualquier cosa que necesite re-procesar la imagen — ej. generar un PDF del lado del cliente) está bloqueado a menos que la configuración de CORS del bucket permita explícitamente el origen que hace la llamada. Las apps móviles nativas haciendo peticiones HTTP directas a la URL firmada no están sujetas a CORS (es una restricción exclusiva del navegador), así que este problema en particular no debería afectar a Abblo Mobile — pero vale la pena saber que la lista de CORS del bucket por ahora solo incluye los dominios de la app web.

Course → Level → Unit → Lesson → Activity

La jerarquía de contenido, de afuera hacia adentro:

1

Course (curso)

GET course/all — la materia de nivel superior (ej. "English"). Se elige una sola vez en la pantalla de bienvenida.

2

Level (nivel)

GET course/{idCourse}/levels — los sub-niveles CEFR de ese curso, cada uno con id, name, ordering, img_big.

3

Units → Lessons → Activities

GET group/{idGroup}/units/activities — todo el árbol de contenido de un nivel se trae en una sola llamada, con el alcance acotado al grupo activo del estudiante. Esta única respuesta se cachea del lado del cliente y se usa para toda la navegación dentro del nivel (actividad siguiente/anterior, estado de desbloqueo, progreso).

4

Una actividad a la vez

Una pantalla de Lección muestra exactamente una actividad. Avanzar solo se permite una vez que la actividad actual tiene has_attemp: true — no se puede saltar sin responder. Retroceder no tiene esa restricción.

Cómo funciona una actividad

Este es el corazón del producto. Un mismo esquema de respuesta del backend es compartido por todas las actividades, y el frontend se ramifica fuertemente según activity_type.code para decidir cómo renderizarla y cómo armar la respuesta que envía.

Si la app llama a attempt o a review para una actividad dada se decide puramente del lado del cliente, a partir del flag has_attemp de esa actividad en el árbol de contenido cacheado: has_attemp ? "review" : "attemp".

Llamar a attempt no es idempotente — pegarle registra un intento nuevo del lado del servidor. El backend lo ha rechazado en pruebas con: "Before creating an attempt, the sum of the contents qualify weigth of the activity must be 100%" — una validación de autoría de contenido, no un bug del cliente, pero vale la pena manejarlo con cuidado en la UI del móvil.

Hay 24 tipos de actividad distintos en producción, cada uno con su propio widget de interacción y su propio esquema de contenido. COMP_S(DND)08 — Complete Sentence (Drag & Drop)words_in_holes

Cómo se parte el %s

El banco de palabras completo sale de un solo lugar: content[0].content_option[0].text, partido por %s y recortado — ej. "blazer %s boots %s coat" → ["blazer","boots","coat"]. Ese arreglo se mezcla una vez (Ramdom()) y se reutiliza como arrayWords para todas las preguntas de la actividad, no una lista distinta por pregunta.

Cada oración (content[i].text, ej. "casual wear: %s %s %s %s") se parte con text.split(/(%s)/) — como la regex usa un grupo de captura, el propio marcador %s queda dentro del arreglo resultante en vez de desaparecer. Eso es lo que le permite a la UI saber exactamente dónde dibujar cada casilla para soltar una palabra, intercalada con el texto literal.

Cómo se interpreta la corrección

El backend no penaliza el orden para este tipo — si el estudiante usó las palabras correctas en cualquier orden, igual regresa percentage === qualify_weigth (100%). El frontend corrige esto por su cuenta con isBlankOrderCorrect(template, userAnswer, rightAnswer): aplica la misma función extractBlanksFromTemplate a la respuesta del usuario y a la right_answer del backend (convierte la plantilla con %s en una expresión regular con grupos (.*?) por cada hueco) y compara, hueco por hueco, si las palabras extraídas coinciden en la misma posición.

resultado = orderCorrect !== null
  ? orderCorrect                                          // comparación propia, por orden
  : Number(item.percentage) === Number(item.qualify_weigth)  // si no se pudo parsear, usa el % del backend

Para el desglose palabra por palabra: si content_option[0].attempt_report.data.results viene vacío (pasa seguido), el frontend lo reconstruye a mano — recorta el prefijo literal de la oración tanto de la respuesta del usuario como de la right_answer, y luego va comparando palabra por palabra contra la lista completa de palabras posibles (ordenadas de más larga a más corta, para no hacer match parcial), marcando cada una "correct"/"wrong" según si coincide exactamente con la de right_answer en esa posición.

Ver Ejemplo real capturado para el JSON crudo completo de este tipo.

COMP_S(SEL)11 — Complete Sentence (Select)words_in_holes

Cómo se parte el %s

sentences = item.text.split(/(%s)/) — igual que DND, conserva el marcador %s en el arreglo para saber dónde va el desplegable. Las opciones del desplegable salen de content_option[0].text.split("%s") (recortadas y mezcladas con Ramdom()) — a diferencia de DND, aquí sí hay un content_option con sus propias opciones por cada pregunta, en vez de un único banco global.

Cómo se interpreta la corrección (la más compleja de toda la app)

El frontend aplica cinco reglas en cascada, en este orden exacto, porque se observó que los campos del backend se contradicen entre sí:

  1. Reconstrucción cuando faltan resultados: si attempt_report.data.results viene vacío pero sí llega user_answer, el frontend recorta el prefijo/sufijo literal de la plantilla alrededor del %s (template.split("%s")) para extraer solo la palabra elegida.
  2. allDetailsCorrect: si cada entrada de results dice "correct" o "right", se considera correcto aunque percentage diga otra cosa.
  3. Comparación de string exacta (la más confiable): si item.answer.trim() === attempt_report.right_answer.trim(), es correcto sin importar nada más — se le da más peso que a cualquier otro campo.
  4. bad_answers_contents_ids: si el id del contenido está explícitamente en esa lista, se marca incorrecto.
  5. Respaldo final: item.percentage > 0 || allDetailsCorrect.
correct = answerMatchesRightAnswer
  ? true
  : isExplicitlyBad
  ? false
  : (item.percentage > 0 || allDetailsCorrect)
W_ANS04 — Write Answermatch_answer

%s: cada content[i].text trae como mucho un %s, que se reemplaza directamente por guiones bajos para mostrarlo: item.text.replaceAll("%s", "____") — es puramente visual, no se usa para extraer nada.

Corrección: no se usa percentage en absoluto. Cada respuesta se clasifica comparando su id contra dos arreglos de nivel superior de la actividad: getCheckAnswer(id, right_answers_contents_ids, bad_answers_contents_ids) devuelve "right", "bad" o "none" según en cuál lista aparezca el id.

ORD_S(DND)03 — Order the Sentence (Drag & Drop)match_answer

Fichas: las palabras a ordenar vienen de content_option[0].text con splitText: true — el componente las separa por su cuenta en la UI (no hay %s aquí, es una sola oración desordenada).

Corrección: item.percentage > 0. El desglose palabra por palabra SÍ viene listo del backend en content_option[0].attempt_report.data.results — el frontend solo recorre esa lista y, para cada palabra marcada "wrong", muestra correct_word en vez de lo que escribió el estudiante.

COMP_S(WRT)12 — Complete Sentence (Writing)words_in_holes

%s: igual que DND/Select, item.text.split(/(%s)/) conservando el marcador, pero aquí cada %s se reemplaza en la UI por un campo de texto en vez de un espacio para arrastrar o un desplegable.

Corrección: item.percentage > 0. El resultado y la plantilla para mostrar el detalle salen directo de content_option[0].attempt_report.data.results / .template, sin reconstrucción propia como en DND.

MAT(LINE)07 — Match (líneas)match_son

questions + answers mezcladas, cada elemento puede ser texto, imagen o audio (el tipo se infiere del widget del content, o de la extensión del archivo en content_type para las respuestas). Corrección: item.percentage > 0, sin comparar contra qualify_weigth.

TREE(DnD)13 — Árbol genealógico (Drag & Drop)match_son

Arrastrar nombres hacia un diagrama de árbol genealógico; las opciones solo llevan content_type (audio), sin texto propio. Corrección: item.percentage > 0.

MAT(DND)05 — Match (Drag & Drop)match_son_multiple

Como el emparejamiento por líneas, pero una pregunta puede tener varias respuestas — se envían como answer: "501,502,503" (ids separados por coma).

Corrección — el único tipo con percentage_details: en vez de leer item.percentage, el frontend parte answer por coma y, por cada id seleccionado, busca su propia entrada dentro de question.percentage_details (un arreglo con un { id, correct } por cada opción posible) — así puede marcar una selección múltiple como "2 de 3 correctas" en vez de un solo booleano para toda la pregunta.

LSTN_REC06 / LSTN_REC0BYROLE7 — Escuchar y grabar / Juego de roles

LSTN_REC06: si item.text contiene %s, se parte en dos con split("%s"): la parte antes es el name (quién habla) y la de después es el text (la línea). Si no hay %s, todo el texto pasa como text y no hay name.

LSTN_REC0BYROLE7 (juego de roles): primero separa observations.split(/(%s)/) para sacar los nombres de los dos roles (roles[0] y roles[2], limpiando HTML inyectado con DOMParser). Luego, por cada línea de diálogo, vuelve a partir item.text por %s para obtener de quién es el turno — y le quita los dos puntos finales ("Emma:" → "Emma") con .replace(/\s*:\s*$/, ""), porque si no, nunca calza exactamente con el nombre sacado de observations y la grabadora no resalta ningún turno.

Corrección: ninguno de los dos se autocalifica — ambos usan getCheckAnswer() contra right_answers_contents_ids/bad_answers_contents_ids, que el backend llena después de que un docente califica el audio manualmente vía activitypercentage/{id}/full.

W_PARAGRAPH19 — Escribir párrafomatch_answer

Escritura libre más larga, sin %s (un solo campo abierto por contenido). Corrección: igual que W_ANS04, vía getCheckAnswer() — calificación manual del docente, lleva activity_percentage.feedback.

W_ANS(Opt_pro)17 — Write Answer (opción pro)

Como W_ANS04 pero no usa getCheckAnswer() — devuelve el percentage crudo de cada respuesta (review.answers[].percentage) y es quien consume el dato el que tiene que decidir un umbral de "correcto".

T_F15 — Verdadero o Falso

%s: el enunciado reemplaza %s por guiones bajos igual que W_ANS04 (text.replace(/\n/g,"").replaceAll("%s","____")); las dos opciones (Verdadero/Falso, o las que sean) salen de content_option[0].text.split("%s"). Corrección: devuelve percentage crudo por respuesta, sin booleano calculado.

M_CHOICE20 — Opción múltiple

MCQ estándar, sin manipulación de %s en el contenido en sí. Corrección: percentage crudo por respuesta. Esta es también la única forma que renderiza el módulo de Tests, sin importar el tipo real de la actividad subyacente — ver Tests.

AUD_PTR_MATCH23 — Emparejar audio e imagen

%s: se reemplaza por guiones bajos igual que W_ANS04/T_F15. Corrección: trae tanto el percentage crudo como, cuando el intento ya se procesó (attempt_report.state === 200), el texto de attempt_report.right_answer para mostrar cuál era la respuesta correcta.

LSTN_AUD01 / LSTN_READ21 / CLK_PTR22 — Sin calificar

LSTN_AUD01 y LSTN_READ21 ni siquiera tienen bloque review — solo reproducir/leer. CLK_PTR22 sí tiene review.answers, pero es solo un arreglo plano de ids de contenido (sin corrección) — autocomprobación, no calificación real.

LSTN10 — Listen

%s: si item.text lo trae, se parte en name/text igual que LSTN_REC06. Corrección (bug conocido): item.percentage === item.qualify_weigth con === estricto — sin el Number() que sí usan otros tipos, así que puede fallar si uno llega como número y el otro como string.

AUD_GREET18 — Saludos en audio

Sin %s en el contenido. Corrección (mismo bug que LSTN10): item.percentage === item.qualify_weigth, comparación estricta sin coerción de tipos.

MAT_CARD_PAIRS16 / MAT_CARD_PAIRS1701 — Memory / Pares extendidosmatch_answer

Cada par content[i] + content_option[0] se aplana en dos "cartas" separadas que comparten un índice match: index, y luego se mezclan juntas en un mazo con Ramdom(). No hay %s ni percentage por carta — la validación de "¿emparejó bien?" es puramente del lado del cliente, comparando que las dos cartas volteadas compartan el mismo match.

BIOC_ACT01 / W_MEDIA02 — Solo informativos

Ninguno de los dos trae objeto review en la respuesta — no son calificables, solo presentan contenido (biografías / video-imagen-audio).

ALPH_NUM09 — Alfabeto o números

Divide content en letters (text.length <= 1) vs. words (text.length > 1), cada uno con su propio audio de pronunciación. Sin %s, sin calificación — es práctica de pronunciación.

Algunas carpetas bajo Activity/ en el repositorio (Challenge1C21, Challenge_1B41, Challenge_1C31, Challenge_1D12, Challenge_2D12, completeSentences) existen pero no están conectadas al switch que elige un componente a partir de activity_type.code. Confirma con el equipo si son legado o están en progreso antes de tratarlas como parte del catálogo real.

process no es un tipo de actividad — es una pista por elemento de contenido que se envía junto con la respuesta, diciéndole al motor de calificación del backend cómo validar esa pieza específica. Aparecen cuatro valores en todo el código:

Enviar respuestas

Un solo servicio compartido (GetResultsActivity) maneja el envío para prácticamente todos los tipos de actividad dentro de una lección. Es un ida-y-vuelta de dos pasos:

1

Enviar las respuestas

    { "id": 102, "id_content_option": 502, "process": "words_in_holes", "answer": "before noon" }
  ]
}

Si tiene éxito, la app también vuelve a pedir todo el árbol de unidad/lección/actividad en segundo plano, para que el estado de desbloqueo y las barras de progreso se actualicen de inmediato.

2

Pedir el desglose calificado

GETactivitypercentage/{id_activity_percentage}

El frontend reduce esto a { totalContents, totalCorrects, totalIncorrects, percentage, answers: [{id, correct}] } para la UI.

Bug de coerción de tipos a tener en cuenta: la corrección se calcula como Number(percentage) === Number(qualify_weigth) en la mayoría de los lugares, específicamente porque el backend envía percentage como número pero qualify_weigth como un string numérico (20 vs "20.00"). Algunos tipos de actividad (LSTN10, AUD_GREET18, y el propio manejador de envío del componente Unscrambell) todavía usan === estricto sin coerción — un bug de corrección latente que el equipo móvil no debería copiar.

Modelo de intentos

No hay ningún contador de intentos del lado del cliente en todo este código base. Los intentos son enteramente estado del lado del servidor, creado como efecto secundario de llamar al propio endpoint de attempt.

actual_attempts

Entero reportado por el backend, por estudiante y por actividad. Cada componente de actividad lo lee para deshabilitar su botón de "repetir" una vez que se llega al máximo.

has_attemp

Booleano en cada nodo de actividad dentro del árbol de contenido. Es la verdadera condición para "modo review vs. attempt" y para si el botón "Siguiente" de la Lección está habilitado — distinto del contador numérico de arriba.

attempt_report

Objeto de detalle por content_option: { state, right_answer, data: { results, user_answer, template } }. Muy explotado por los tipos de actividad de arrastrar/ordenar/seleccionar para armar desgloses correcto/incorrecto palabra por palabra.

MAX_ATTEMPTS

Constante del lado del frontend, no se pide al backend: 5 en producción, 100 en el build de dev. Una vez que actual_attempts >= MAX_ATTEMPTS, los botones de reintentar desaparecen.

Sobre average_attempts: no existe en ninguna parte de la lógica de este frontend — es un agregado de solo reporte que viene pre-calculado desde group/{idGroup}/me_skills (ver Progreso). No hay ninguna fórmula que portar; trátalo como un valor del backend para mostrar, no para calcular.

El módulo de Tests

Un Test es simplemente la última lección de una unidad, presentada de forma distinta: como una secuencia de actividades dentro de un wizard a pantalla completa, en vez de una actividad por página.

Límite de alcance importante

Sin importar el activity_type.code real de la actividad subyacente, la UI de Tests solo renderiza un widget de opción múltiple. El rico catálogo de 24 tipos de arriba es un concepto exclusivo de Lección — los Tests aplanan todo a MCQ.

El endpoint de envío es distinto

POST activity/{id}/answers — sin el segmento /group/{idGroup}/, a diferencia del endpoint de envío de Lección. Fácil de pasar por alto al portar.

Semántica de reintentos

  • Por actividad, a mitad del test: sin reintento — una vez respondida, se avanza a la siguiente actividad de la secuencia.
  • Todo el test: "Repetir Test" reinicia todo el wizard, limitado por el mismo MAX_ATTEMPTS (5 prod / 100 dev) contra el propio contador de intentos del test.

Modal de nivel completado

Al terminar un test se revisa si hay una lección o unidad siguiente en el árbol de contenido. Si de verdad no queda nada, se dispara un modal de felicitación: "Congratulations, level completed!" — este es el único lugar en toda la app con una celebración explícita de "ya terminaste". La navegación normal de Lección/Unidad no tiene equivalente — ahí la completitud siempre es implícita (todas las actividades tienen has_attemp en true), sin ninguna pantalla o evento dedicado de "lección completada".

Problemas a tener en cuenta antes de portar

  1. Sin flujo de refresh-token. Un solo 401 en cualquier parte borra toda la sesión. Decidan si el móvil quiere el mismo comportamiento o algo más suave.
  2. Login y /user/me tienen formas distintas. El login es plano; /user/me anida los campos de perfil bajo profile. No asuman un solo esquema para "el objeto usuario".
  3. Bug de coerción de tipos en las comparaciones de calificación (percentage como número vs. qualify_weigth como string) — corregido en la mayoría de lugares con Number(), no en todos.
  4. UI de 6 niveles hardcodeada en la web, a pesar de que el curso real tiene más niveles (10 vistos en vivo). No copien este límite.
  5. Dos campos de Redux muertos — idsActivities y dataCompleteActivities están declarados pero nunca se llenan en ninguna parte del código. No asuman que llevan datos reales si consultan el código fuente web.
  6. Los Tests solo renderizan Opción Múltiple sin importar el tipo real de actividad por debajo — una simplificación deliberada (o quizás incompleta) que vale la pena decidir como producto para el móvil.
  7. Sin evento explícito de "lección/unidad completada" fuera del modal de nivel completado del módulo de Tests — en lo demás, la completitud es solo un estado inferido.
  8. average_attempts solo existe pre-calculado en el endpoint de reporte me_skills — no hay ninguna fórmula que replicar del lado del cliente.
  9. Algunos endpoints reusan un mismo nombre de recurso para cosas muy distintas — ej. group es la ruta base para unidades/actividades, calificaciones, posición, contraseña, actividades pendientes, y el reporte Excel. endpoints.ts por sí solo no distingue esto; el sufijo que discrimina está hardcodeado en cada punto de llamada.
